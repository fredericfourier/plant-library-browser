# Plant library workflow and approval contract

Audience: any future coding agent or maintainer (not Claude-specific). This is the **primary artwork contract**. The private
Border Designer repository documents how its engine consumes this library in `docs/E3_PLANT_CATALOGUE_ARTWORK_INTERFACE.md` and must not restate
or contradict the approval rules below.

Related: `docs/BOTANICAL_VERIFICATION.md` (record formats), `docs/BOTANICAL_STATUS.md` (status manifests and generation queue), `README.md`.

## 1. Approval contract (permanent)
1. **Visual approval belongs to the exact published WebP SHA-256 hash.** Not to a plant id, a filename, a record or a PNG master.
2. **`data/approval-ledger.json` is the authoritative, append-only approval history.** Entries `{variant, plantId, imageSha256, approvedAt, ...}` are never
   edited or removed. The only way an approval ends is an explicit `revocations` entry made at the owner's request (`approval_ledger.py revoke ... --reason`).
3. **PNG-master integrity is a separate, NON-BLOCKING maintenance concern** (`sourceIntegrity` in the status manifests, `blocking: false`). A missing,
   stale or unregistered PNG master never changes approval, queue membership, rendering or customer eligibility of published artwork.
4. **Rebuilding status, importing assets, exporting catalogues or running CI cannot revoke approval of unchanged WebP bytes.** A record reset by a tool
   is reported by `approval_ledger.py check`; the ledger keeps the approval.
5. **Changed WebP bytes never inherit previous approvals.** They show as `approval_for_other_bytes` (status `pending_review`/`uncertain_match`) until approved again.
6. **Replacement artwork the owner has already accepted** is recorded with `approval_ledger.py accept`, using the existing owner decision and
   truthful provenance (superseded hash and its original timestamp kept). No new visual review is implied or required.
7. **Never fabricate approval records and never overwrite historical timestamps.** `approvedAt` of an `accept` entry is the time the owner's decision was
   recorded, with `basis` naming the decision; the older approval stays in its own entry.
8. **One explicit visual approval per final artwork version** for a new plant (`approval_ledger.py approve`). No overlapping approval stages: that one command
   writes the ledger entry and keeps `data/botanical-verification.json` in step.

| `assets/plant-watercolours/<id>.webp`, `<id>-watercolour.webp` | Published botanical and watercolour WebPs |

| `data/botanical-status.json`, `data/watercolour-status.json` | Derived status manifests (`status`, `visualApproval`, `sourceIntegrity`) |

| `tools/botanical_status.py` | Build/check/queue the status manifests (`--type watercolour` for the watercolour variant) |

## 3. Workflows
Always work on an isolated branch (never `main`); nothing here authorises a merge, deploy or push.

**Add a catalogue record.** Edit the canonical catalogue in the private repository and re-export `data/plants.json` (do not hand-edit). Add the id to a batch in
`data/additions.json`. Then `python3 tools/check_catalogue_sync.py`. The status manifests list the plant as `missing` until artwork is published.

**Prepare artwork.** Botanical and watercolour illustrations are separate images. Dimensions come from the catalogue record: the 10 px/cm convention
(`watercolourEnvelope.canonicalHeightPx = 10 x heightCm`, `expectedSpreadPx = 10 x spreadCm`, `ratioTolerance`, `hardFailTolerance`). Artwork is never stretched or
squashed to fit; large proportion differences are flagged to the owner, not fixed by distortion. No artwork is regenerated by tools.

**Register dimensions and asset metadata, publish WebPs.** Preferred for one image: the private repository's publisher
(`./tools/publish-watercolour <id> <png> --kind watercolour|botanical --plb-root <this checkout>` is a read-only preview; `--publish` needs the printed tokens).
Batch watercolours: `python3 tools/import_watercolour_assets.py <plb-root> <bd-root|-> data/plants.json <report.json> <extracted-part-dir> [...]`.
Both copy bytes unchanged, update `manifest.json` and the verification record as `awaiting_review`, and keep any replaced record (with `approvedAt`) under `previous`.
There is no separate botanical batch importer: botanical WebPs are published with the publisher or copied byte-for-byte with their manifest and record entries.

**Record owner visual approval (one step).**
```
python3 tools/approval_ledger.py approve watercolour <plant-id> [...]      # or: botanical
python3 tools/botanical_status.py build && python3 tools/botanical_status.py --type watercolour build
```
The hash is read from the published file. Do this only on the owner's decision.

**Replace previously approved artwork.** Publish the new WebP (previous record kept). Then exactly one of:
- the owner reviews it: `approval_ledger.py approve <variant> <id>` (new hash, new approval); or
- the owner has already accepted these exact bytes: `python3 tools/approval_ledger.py accept <variant> <id> --sha256 <new> --supersedes <old approved hash> --basis "<owner decision and where recorded>" --at <UTC time the decision was recorded>`.
Until then the plant shows as not approved for the new bytes; the old bytes stay approved.

**Status rebuild and integrity tests.**
```
python3 tools/botanical_status.py check && python3 tools/botanical_status.py --type watercolour check
python3 tools/approval_ledger.py check --base origin/main        # append-only vs the base branch; no tool revoked an approval
python3 tools/check_catalogue_sync.py
python3 tools/test_approval_lifecycle.py        # lifecycle contract for both illustration types
python3 tools/test_illustration_status.py && python3 tools/test_watercolour_import.py && python3 tools/test_e3_v12_additions.py
python3 tools/test_browser_availability.py      # needs Playwright + Chromium + Pillow; skipped otherwise
```
CI (`.github/workflows/validate-catalogue-sync.yml`) runs the ledger check, both manifest checks and the lifecycle tests.

**Synchronise with Border Designer.** The engine reads published WebPs pinned to a commit of this repository and requires the image to be approved for the exact published hash (status `approved` /
record `confirmed` with a matching `imageSha256`). Master PNGs are not read. See the private repository's `docs/E3_PLANT_CATALOGUE_ARTWORK_INTERFACE.md`.

**Preserve approval and provenance history.** Keep `previous` chains, `sourceMasters`, `approvedOriginalImageSha256`, ledger entries and `supersededApprovedAt`. Do not rewrite Git history of these files.
